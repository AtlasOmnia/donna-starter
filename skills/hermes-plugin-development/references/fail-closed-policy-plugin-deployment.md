# Live Deployment of Fail-Closed Hermes Policy Plugins

Use this when a Hermes backend plugin enforces profile/root/tool policy and therefore must be installed atomically, verified in fresh processes, and activated through a gateway restart without trusting the deploying controller's narrative.

## Treat the library and deployment package as different artifacts

A reviewed Python library may have no live `plugin.yaml`, registry, or installation wrapper. Keep the candidate repository immutable. Build deployment-only artifacts under a separate evidence root:

- `plugin.yaml` with the exact live `provides_hooks` and tool declarations;
- a minimal wrapper `__init__.py` that passes canonical registry/audit paths to the vendored package;
- package files vendored from the verified wheel/source, never imported from a mutable checkout;
- one shared canonical registry and metadata-only audit path;
- before/after profile snapshots and executable rollback instructions.

Hash the staged payload before touching live profile homes.

## Registry generation must deduplicate by Git identity

Project names and campaign labels are not ownership identity. Multiple labels can resolve to one canonical Git root/common directory. Generate entries through the library's scanner, then deduplicate by canonical root/common-directory identity before registry validation. Preserve multiple worktree roots only when the schema represents them under one project.

Fail closed on:

- duplicate canonical roots;
- missing/moved roots;
- ambiguous symlink/realpath resolution;
- mixed roots in one mutation;
- unknown profile ownership;
- unresolved incumbent writers.

Do not weaken uniqueness validation just to make a campaign registry load.

## Stage and canary before live copy

Before installation, require from the exact staged bytes:

1. compile/import/register success;
2. `pre_tool_call` plus expected controlled tools registered;
3. default-profile mutation blocked before handler execution;
4. general execution routed to the controlled-tool requirement;
5. assigned specialist/root allowed only when ownership is clear;
6. wrong profile/root, mixed roots, incumbent conflict, missing registry, and malformed registry blocked;
7. plugin and registry hash matches;
8. tampered or missing plugin refused by an external startup checker.

Hermes isolates hook exceptions, so an importable plugin can still fail open at runtime. An independent startup prerequisite and actual hook canary are mandatory.

## Install per profile, then verify in fresh processes

Profile homes have independent plugin discovery/configuration. For every in-scope profile:

1. Snapshot config and plugin tree without copying `.env` or secrets.
2. Copy the complete staged directory into same-filesystem sibling staging.
3. Atomically rename into `$HERMES_HOME/plugins/<name>`.
4. Verify every immutable payload file against the staged manifest.
5. Enable through supported Hermes CLI/config operations, preserving existing enabled/disabled entries.
6. Start a fresh process and run `hermes [--profile NAME] plugins list --plain --no-bundled`; current processes do not retroactively load the plugin.
7. Run a harmless policy decision matrix under the fresh profile identity.

An initial `plugins enable` may report “not installed” if discovery occurred before the atomic copy was visible to that process. Do not accept or reject from that message alone. Re-run discovery in a fresh process, verify the enabled entry, and confirm the hook/tool canaries. Conversely, a list entry alone is not proof the hook executes.

## Compare immutable payloads, not runtime caches

Importing Python plugins creates `__pycache__/` and `.pyc` files. Whole-directory hashes taken after load will therefore differ from pristine staging even when every deployed source/metadata byte is correct.

Use two comparisons:

- **Immutable payload:** allowlisted staged files only; require equal file count, per-file hashes, and deterministic tree hash across every profile.
- **Runtime residue:** classify generated bytecode/cache files separately; they are expected unless policy forbids them.

Treat the authorized `plugins.enabled` config change as an intended delta, not byte instability. Reconcile it by semantic config readback plus fresh plugin discovery. Do not override a successful deployment with a controller HOLD whose only mismatches are generated bytecode and the intended enable entry.

## Gateway activation and incumbent sessions

After all fresh CLI/profile canaries pass:

1. Reconfirm no campaign is mid-write.
2. Restart the gateway through its supported owner command.
3. Verify launch supervisor PID/state, gateway health, actual hook count, connected platforms, cron scheduler, and dispatcher.
4. Distinguish pre-existing multiplex/profile warnings from new plugin failures.
5. Run a harmless gateway/profile-scoped policy canary.
6. Preserve the old TUI/session history, but mark it stale: a process created before activation cannot be trusted to have loaded the guard. Require a fresh TUI/session before protected controller work continues.

## Independent closeout

A controller exit code or final prose is provisional. Independently verify:

- all scoped profiles report enabled in fresh CLI discovery;
- installed immutable payload hashes equal staging;
- startup/tamper/missing-plugin canaries;
- policy decision matrix;
- metadata-only audit with zero privacy violations;
- gateway hook count and health;
- cron/dispatcher health;
- rollback artifacts.

If a controller returns HOLD after successful live activation, inspect the exact mismatch before rolling back. Generated caches, intentional config deltas, or stale in-process discovery are reconciliation issues; source-byte drift, failed hook loading, wrong policy outcomes, or unhealthy gateway state are true rollback triggers.
